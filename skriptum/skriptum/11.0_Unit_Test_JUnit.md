# 11.0 Unit-Tests mit JUnit

**Unit-Tests** prüfen einzelne Bausteine (Units) deines Programms – meist eine Methode oder eine Klasse – automatisch. Statt dein Programm immer manuell zu starten und auszuprobieren, kannst du mit Tests sicherstellen, dass dein Code auch nach Änderungen weiterhin korrekt funktioniert.

**JUnit** ist das am weitesten verbreitete Test-Framework für Java. In diesem Kapitel lernst du, wie du JUnit in einem Maven-Projekt einsetzt – und damit auch, wie du externe Bibliotheken (Dependencies) über Maven in dein Projekt bringst.

## Maven – Projekt- und Build-Management

**Maven** ist ein Build- und Projektmanagement-Tool für Java. Es automatisiert das Kompilieren, Testen und Paketieren (z. B. als `.jar`) und verwaltet **Abhängigkeiten** (externe Bibliotheken wie JUnit) zentral – genau das brauchen wir, um JUnit für die Tests verfügbar zu machen.

### Grundidee von Maven

Maven folgt dem Prinzip **"Konvention vor Konfiguration"**: Ein Maven-Projekt hat eine feste Struktur, die du nicht selbst festlegen musst:

```
mein-projekt/
├── pom.xml                      ← Zentrales Konfigurationsfile (dort liegen Dependencies)
├── src/
│   ├── main/
│   │   ├── java/                ← Java-Quellcode (Package-Struktur)
│   │   └── resources/           ← Konfigurationsdateien (z. B. persistence.xml)
│   └── test/
│       └── java/                ← Tests (hier landen deine JUnit-Tests)
└── target/                      ← Von Maven generiert (classes, jar)
```

Das Herzstück ist die Datei **`pom.xml`** (Project Object Model). Sie beschreibt:
- **`groupId`** – Organisation/Firma (z. B. `com.example`)
- **`artifactId`** – Name des Projekts (z. B. `medical`)
- **`version`** – Versionsnummer (z. B. `1.0-SNAPSHOT`)
- **`dependencies`** – externe Bibliotheken, die Maven automatisch herunterlädt

### Maven-Projekt erstellen

In **IntelliJ IDEA** erstellst du ein Maven-Projekt so:

1. **New Project** → wähle **Maven** als Build-System (statt IntelliJ)
2. Wähle dein installiertes **JDK**
3. Als `groupId` gibst du z. B. `com.example`, als `artifactId` `medical` ein
4. IntelliJ erzeugt automatisch die `pom.xml` mit der Standardstruktur `src/main/java`, `src/main/resources` und `src/test/java`

Alternativ kannst du mit der leeren `pom.xml` auch per Kommandozeile arbeiten:

```xml
<project xmlns="https://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>medical</artifactId>
    <version>1.0-SNAPSHOT</version>
</project>
```

### Dependencies hinzufügen – JUnit einbinden

Externe Bibliotheken fügst du in `pom.xml` innerhalb von `<dependencies>` ein. Damit Maven deine Tests kennt, ergänzt du die JUnit-Abhängigkeit mit dem Scope **`<scope>test</scope>`**. Der Scope gibt an, wo eine Bibliothek benötigt wird:

- **`compile`** (Standard) – für den normalen Programmcode, ist auch später im fertigen Programm enthalten
- **`test`** – nur für die Tests, wird **nicht** Teil des ausgelieferten Programms

```xml
<dependencies>
    <!-- JUnit 5 für Unit-Tests -->
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.10.2</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

Nach dem Einfügen lädst du die Dependencies herunter (in IntelliJ: **Maven-Fenster → Reload All Maven Projects**, oder das Icon mit den zwei Pfeilen). Maven lädt die Bibliothek automatisch vom zentralen Repository (**Maven Central**) in deinen lokalen Cache (`~/.m2/repository`).

So funktioniert das Herunterladen: Maven sucht jede Dependency über `groupId` + `artifactId` + `version` im Maven Central Repository. Du musst **keine `.jar`-Dateien manuell** herunterladen oder einem Klassenpfad hinzufügen.

### Wichtige Maven-Grundbegriffe

| Begriff | Bedeutung |
|---------|-----------|
| **Dependency** | Eine externe Bibliothek, die dein Projekt benötigt |
| **Scope** | Wo eine Bibliothek gebraucht wird (`compile`, `test`, ...) |
| **Repository** | Zentraler Ort, aus dem Maven Bibliotheken lädt (z. B. Maven Central) |
| **local repository** | Lokaler Cache unter `~/.m2/repository` – einmal geladen, wird offline weiterverwendet |
| **Build** | Der Prozess aus Kompilieren, Testen, Paketieren |
| **Lifecycle** | Feste Reihenfolge von Phasen (`compile`, `test`, `package`, ...) |
| **Transitive Dependencies** | Maven lädt automatisch auch die Bibliotheken, die deine Dependencies selbst benötigen |

### Typische Maven-Befehle

```bash
mvn clean          # Löscht den target-Ordner (frischer Build)
mvn compile        # Kompiliert den Quellcode
mvn test           # Führt die Tests aus (führt vorher compile aus)
mvn package        # Erzeugt ein jar/war im target-Ordner (inkl. compile + test)
mvn clean package  # Häufigste Kombination: sauber bauen und paketieren
mvn dependency:tree  # Zeigt alle (auch transitiven) Dependencies als Baum
```

`mvn test` führt alle JUnit-Tests aus – das Ergebnis siehst du in der Konsole, z. B. `Tests run: 3, Failures: 0, Errors: 0, Skipped: 0`.

## Unit-Tests schreiben

### Aufbau eines JUnit-Tests

Ein Test ist eine eigene Klasse, die im **Test-Quellordner** `src/test/java` liegt (nicht in `src/main/java`!). Für das medizinische Beispiel testen wir die Klasse `Patient`:

```java
package com.example.medical.model;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class PatientTest {

    @Test
    void getName_returnsTheName() {
        Patient p = new Patient("Anna", 25, "Hypertonie");

        assertEquals("Anna", p.getName());
    }
}
```

Wichtige Bausteine:

| Baustein | Bedeutung |
|----------|-----------|
| `@Test` | Markiert eine Methode als Test. JUnit führt jede so markierte Methode automatisch aus |
| **Testklasse** | Konvention: Name der Klasse + `Test` (z. B. `PatientTest`) |
| **Testmethode** | Meist `void` und beschreibend benannt (z. B. `getName_returnsTheName`) |
| `assertEquals` | Prüft, ob zwei Werte gleich sind. Ist die Prüfung fehlgeschlagen, schlägt der Test fehl |
| `src/test/java` | Ablageort der Testklassen (getrennt vom Produktionscode) |

### Wichtige Assertions

**Assertions** sind die Prüfungen, die du in einem Test durchführst. Sie stammen aus `org.junit.jupiter.api.Assertions`:

```java
assertEquals(25, p.getAge());                    // Gleichheit
assertNotEquals(30, p.getAge());                 // Ungleichheit
assertTrue(p.isAdult());                         // true
assertFalse(p.isAdult());                        // false
assertNull(obj);                                 // null
assertNotNull(obj);                              // nicht null
assertSame(a, b);                                // gleiche Referenz
assertNotSame(a, b);                             // unterschiedliche Referenz
assertThrows(IllegalArgumentException.class,     // erwartete Exception
             () -> p.setAge(-5));
assertArrayEquals(new int[]{1, 2}, new int[]{1, 2});  // Array-Inhalt
```

Grundregel: Du schreibst immer **erwarteter Wert zuerst**, dann den tatsächlichen (`assertEquals(expected, actual)`).

### Executable-Code als zweites Argument: `assertThrows`

`assertThrows` prüft, ob der übergebene Code-Block eine bestimmte Exception wirft. Der Code wird als **Lambda-Ausdruck** (`() -> ...`) übergeben, damit JUnit ihn ausführen und die Exception abfangen kann:

```java
@Test
void setAge_rejectsNegativeAge() {
    Patient p = new Patient("Anna", 25, "Hypertonie");

    assertThrows(IllegalArgumentException.class,
                 () -> p.setAge(-5));
}
```

Der Test besteht, wenn der `setAge(-5)`-Aufruf eine `IllegalArgumentException` wirft. Wird keine Exception geworfen, schlägt der Test fehl.

### Test-Lebenszyklus: `@BeforeEach`

Wenn mehrere Tests dasselbe Ausgangsobjekt brauchen, erstellst du es mit einer Methode, die mit **`@BeforeEach`** markiert ist. Diese Methode läuft **vor jedem einzelnen Test** und liefert so einen frischen Ausgangszustand:

```java
class PatientTest {

    private Patient p;

    @BeforeEach
    void setUp() {
        p = new Patient("Anna", 25, "Hypertonie");
    }

    @Test
    void getName_returnsTheName() {
        assertEquals("Anna", p.getName());
    }

    @Test
    void getAge_returnsTheAge() {
        assertEquals(25, p.getAge());
    }
}
```

Damit ist jeder Test unabhängig vom Zustand der anderen – ein häufiger Fehler wäre, ein Feld direkt in der Klasse zu initialisieren, das dann von mehreren Tests gemeinsam verändert wird.

## Test durchführen

In **IntelliJ IDEA** kannst du Tests direkt ausführen:

1. Klicke mit der rechten Maustaste auf die Testklasse (oder auf eine einzelne `@Test`-Methode) und wähle **Run**
2. Alternativ über `mvn test` in der Kommandozeile
3. Das Ergebnis erscheint im Run-Fenster mit grünen (bestanden) und roten (fehlgeschlagen) Balken

Bei einem fehlgeschlagenen Test zeigt dir JUnit den erwarteten und den tatsächlichen Wert an, sodass du den Fehler schnell findest.

## Zusammenfassung

### Wichtige Begriffe
- Maven (`pom.xml`, `groupId`, `artifactId`, `version`, `dependencies`)
- Dependency / Scope (`compile`, `test`) / Repository (Maven Central, local repository `~/.m2`)
- JUnit (`@Test`, `@BeforeEach`)
- Assertions (`assertEquals`, `assertTrue`, `assertThrows`, ...)
- `src/main/java` vs. `src/test/java`
- `mvn test`, `mvn clean package`, `mvn dependency:tree`

### Das sollst du können
- Ein Maven-Projekt erstellen und eine Dependency (z. B. JUnit) in `pom.xml` einfügen
- Grundlegende Maven-Begriffe und -Befehle erklären
- Eine JUnit-Testklasse im Ordner `src/test/java` schreiben
- Die wichtigsten Assertions verwenden
- `assertThrows` zum Prüfen von Exceptions einsetzen
- `@BeforeEach` für einen frischen Ausgangszustand verwenden
- Tests in IntelliJ und per `mvn test` ausführen
